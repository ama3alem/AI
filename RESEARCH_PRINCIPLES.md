# RESEARCH PRINCIPLES

The constraints in this document govern how the system is described, what it is allowed
to claim, and what evidence is required before a claim may be made. They are not
aspirational. Several are enforced in code, and the enforcement points are named.

---

## 1. What this system measures

The system models **observable interaction behaviour** in a digital learning setting:
response latency, accuracy, attempt and skip patterns, navigation, inactivity, and
content-consumption behaviour — measured per learner, over time, relative to that
learner's own history.

## 2. What this system does not measure

Interaction telemetry does not reveal cognition. The system therefore does not, and will
not, claim to:

- read attention, detect consciousness, or infer mental state;
- know what a learner is thinking, feeling, or intending;
- diagnose a psychological, cognitive, or medical condition;
- measure motivation, interest, or emotion.

Anyone asserting that an interaction-timing model can do these things is mistaken about
what the data contains. The distinction is not a matter of degree or of model quality.

### 2.1 Permitted vocabulary

| Use | Avoid |
|---|---|
| behavioural engagement | focus, attention |
| interaction behaviour | mental activity |
| engagement trajectory | cognitive state |
| behavioural deviation | distraction |
| session state | mind state |
| intervention response | behaviour change *(implying causation)* |
| prediction, estimate | detection, diagnosis |
| uncertainty, confidence | certainty |

`BehavioralEngagementState` is the canonical enum. A unit test asserts that no member
name contains a term implying an internal mental state, so the constraint survives
refactoring rather than living only in this document.

## 3. Label provenance

Not all labels are equal, and the difference is not cosmetic. Four kinds exist, and they
are never interchanged:

| Provenance | Meaning | Present in this repository? |
|---|---|---|
| `GROUND_TRUTH` | Independently established by a measurement or design external to the model. | **No.** No ground truth exists. |
| `PROXY_LABEL` | Constructed from observable proxies because the construct of interest is not directly measurable. Valid only to the extent the proxy assumption holds. | `IMPLEMENTED` (`schemas/primitives.py`) |
| `SYNTHETIC_LABEL` | Generated by the simulator from its own generative parameters. | `IMPLEMENTED` (`schemas/primitives.py`, `simulator/`) |
| `MODEL_PREDICTION` | Output of a trained model. Carries uncertainty; never a measurement. | `IMPLEMENTED` (`schemas/primitives.py`, `models/`) |
| `OBSERVED` | Measured directly from an event stream. | `IMPLEMENTED` (`schemas/primitives.py`, `events/`) |

**A synthetic label is never ground truth.** A simulator-generated label encodes the
simulator's assumption about behaviour. Scoring a model against it measures whether the
model recovered the simulator's generative rules — a software property, not a fact about
people.

`DataOrigin` is a permanent property of every value, so a synthetic artifact remains
self-identifying after it is copied, concatenated, or reloaded by a tool that never read
the documentation.

---

## 4. Synthetic data

Every synthetic dataset carries `SYNTHETIC DATA — NOT REAL STUDENT DATA` **in the data**,
not only in prose, via `SyntheticDataStamp`.

The simulator exists to validate **software and architecture**: that the pipeline runs,
that features are deterministic, that baselines mature correctly, that leakage tests
detect leakage, that the API rejects malformed input. It is not a scientific instrument.

### 4.1 The self-fulfilling-label problem

A model can achieve excellent metrics against synthetic labels while learning nothing
real, because the labels were generated by rules the model can recover. The mitigation
is to hold out whole *archetypes* rather than random rows, and to report the resulting
metrics as pipeline metrics. This limitation is stated in `FOUNDATION_STATUS.md` and must
not be quietly dropped as the project grows.

### 4.2 No real data exists

As of this phase the repository contains **no real learner data**. Every metric that
exists is measured against synthetic labels. No such metric may be presented as evidence
about human behaviour.

## 5. Correlation, intervention, and causation

An observed before/after difference following an intervention is an **observed outcome**.
It is not evidence that the intervention caused it.

Reasons, concretely:

- the prediction itself selected who received the intervention, so treated and untreated
  groups differ systematically before any treatment;
- a learner who declines improves on their own;
- the measurements immediately following an intervention are not comparable to those
  before it, because the intervention changed what was being measured.

Causal language requires a controlled design with predefined outcomes and predefined
analysis — randomisation, or a defensible quasi-experimental assignment. The data model
is designed so such experiments can be run later (`PLANNED — NOT IMPLEMENTED`). Until one
exists, intervention records are labelled `observed outcome`, and the intervention
response profile is a **prior over response**, not a measured treatment effect.

---

## 6. Personalization must be earned

Personalization is not assumed to help. A personalised model is a more complex model
fitted to less data per learner, so it can plausibly be *worse* than a population model
until enough history exists.

The architecture therefore requires a direct comparison: population-only features versus
population-plus-personal-baseline features, on the same splits, with the same metric
suite. Personalization is claimed only if that comparison shows a difference. This
comparison is `PLANNED — NOT IMPLEMENTED`.

Relatedly, the baseline engine reports a **maturity level** (`NEW`, `EARLY`,
`DEVELOPING`, `ESTABLISHED`), and the uncertainty engine caps confidence while the
baseline is immature. A learner with thirty seconds of history does not receive a
confidence comparable to one with three weeks.

---

## 7. Uncertainty must be real

The engine is permitted — and required — to answer `UNKNOWN` or `INSUFFICIENT_DATA`.

- A confidence number must be derived from something: calibrated model output, evidence
  volume, and baseline maturity. A number invented for appearance is a defect.
- `INSUFFICIENT_DATA` and `UNKNOWN` are different states with different remedies: the
  first needs more data, the second needs a different or better model.
- Baseline maturity caps confidence independently of the model's own output, so a
  confident model cannot launder a thin history into a confident prediction.

---

## 8. No novelty claims

This project does not claim to be first, unique, impossible to copy, or scientifically
proven. No such claim has been independently verified here.

The intent is to engineer a genuinely differentiated architecture. Whether any element is
novel relative to prior art is a **separate research task** that has not been performed.

No competitor, paper, patent, or benchmark is referenced anywhere in this repository,
because none has been verified. Inventing one would be a fabrication.

---

## 9. Engineering complete ≠ scientifically validated

These are different milestones and are tracked separately:

- **ENGINEERING COMPLETE** — the component exists, is tested, and behaves as documented.
- **SCIENTIFICALLY VALIDATED** — the component's behaviour has been demonstrated to hold
  on real learner data against a predefined evaluation, by a design capable of supporting
  the claim.

Nothing in this repository has reached the second milestone. `FOUNDATION_STATUS.md`
records the first for each component and marks the second as not reached.

---

## 10. No premature complexity

Deep learning, reinforcement learning, and LLM-in-the-loop components are excluded until
experiments justify them. Before any such addition, five things must be demonstrated:

1. behavioural signal exists in the features;
2. the features are individually meaningful;
3. personalization measurably helps;
4. temporal modelling measurably adds value over static features;
5. interventions produce measurable, repeatable outcomes.

None of these is yet demonstrated. Adding a sequence model before step 1 produces an
impressive model of a signal nobody has shown is there.

---

## 11. Data minimisation

Collect only what the stated purpose requires. The data model is designed around
pseudonymous identifiers, with no name, email, precise location, device fingerprint, or
unrelated browsing data. See `PRIVACY.md`.

A feature that would constitute surveillance beyond the stated purpose — tracking a
learner across contexts, devices, or sessions they did not choose to expose — is out of
scope regardless of how predictive it might be.

## 12. Enforcement points

| Principle | Enforced in |
|---|---|
| No directly identifying identifier | `schemas/primitives.py` — identifier character class; unit tests |
| No naive timestamp | `schemas/primitives.py` — `Timestamp` validator |
| Synthetic ≠ ground truth | `schemas/primitives.py` — `Provenance`; unit tests |
| Synthetic-only model cannot be `VALIDATED`/`PRODUCTION` | `schemas/versioning.py` — `ModelRecord` validator |
| No internal-mental-state vocabulary | `schemas/primitives.py` — `BehavioralEngagementState`; unit test asserting state names |
| In-band synthetic marking | `schemas/primitives.py` — `SyntheticDataStamp` |
| No secrets in source or logs | `configuration/settings.py`, `utils/logging.py` |
| No unauthenticated production start | `configuration/settings.py` — `validate_for_runtime` |
| No magic numbers in decisions | `configuration/thresholds.py` — every threshold named and justified |
| Reproducibility | `utils/determinism.py`, `schemas/versioning.py` — `ReproductionStamp` |
